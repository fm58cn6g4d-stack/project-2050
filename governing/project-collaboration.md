## Merging: three tiers

Approved by Espen on October 26 as a design; this section takes effect when they merge the PR that adds it. Agents merge routine work themselves through the merge gate; Espen stays the gate for decisions and headline numbers. The machine-readable copy is `.github/merge-policy.json`; [the setup checklist](agent-automation-setup.md) lists the GitHub settings Espen controls.

| Tier | What | How it merges |
| --- | --- | --- |
| 1. Auto-merge | Research and source files, reviews and data files in the author's claimed paths; scripts whose generated outputs do not change; queue status updates; wording fixes (same numbers and policy IDs), including in domain files | When the required checks pass and another agent has reviewed the current head |
| 2. Auto-merge and notify Espen | Regenerated model outputs whose headline numbers stay within tolerance (each within 1%, the 2040 margins within 0.005% of GDP); domain design changes that keep the same programs; anything not listed elsewhere | As tier 1; the gate then posts the headline deltas to Espen and the daily digest lists the merge |
| 3. Always Espen | `governing/`; adopted inputs (`index/data/inputs/`, including `recovery-adoption.json`); any change to a D3 or D4 test result or to a 2040 margin; new or removed programs (policy IDs added to or dropped from a domain file); the merge rules, checks and agent entry files (`.github/`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`); anything labeled `needs-espen` | Only after Espen adds the `espen-approved` label themselves. New commits after their label remove it, unless the new commit only merges in `main` |

The gate assigns the tier from the PR's changed paths and the headline numbers in the committed outputs; the highest tier among the changes wins. A PR's tier can be raised (label `needs-espen`) but never argued down; if the gate misclassifies, fix `.github/merge-policy.json` in its own tier-3 PR. Keep tier-1/2 work in separate PRs from tier-3 work so routine work is not held behind a decision.

**Required checks.** `rebuild-and-tests` runs the common rebuild as a dry run, fails if a generated file under `index/` no longer matches its inputs, and runs the focused test suites. `merge-tier` passes for tiers 1-2, and for tier 3 only with Espen's label. `agent-review` passes when another agent has approved the current head. Draft PRs and PRs labeled `hold` never merge; mark a PR ready for review when it is done.

**Path ownership.** Authors write within their claimed paths (the queue and the PR's description). The owner map in the policy file names the current owners: Codex for the shared fiscal model and its outputs, Claude Code for capacity, climate-portfolio and review paths, Espen for governing records and adopted inputs. A PR that touches another agent's owned paths needs that owner's review. Ownership is temporary write coordination, as in step 3, and changes through the queue and the policy file.

**Cross-agent review.** Every agent posts as Espen's GitHub account, so GitHub cannot tell agents apart and its own approving review is unavailable. Each PR description states its author on its own line, `Agent-Author: <claude-code|codex|gemini> <session or task id>`. A reviewing agent reads the actual diff at the current head and, if satisfied, comments three lines: `Agent-Review: approve` (or `changes-requested`), `Reviewed-Head: <full head SHA>`, `Reviewer: <agent> <session or task id>`. A different session of the same vendor counts as another agent; the author's own session does not. A review counts only with those three lines; prose review notes do not, and the gate comment flags another agent's comment that has no verdict lines. A new push needs a new approval, except a push that only merges in `main` and leaves the PR's own changes identical, which keeps its approvals (the checks still re-run). A request for changes stands across later pushes until the same reviewer approves, and Espen's `espen-approved` label does not override it: to merge over an open objection, Espen adds `espen-override`, which cancels the objection only: an approving review is still needed (on tier 3, Espen's `espen-approved` stands in for it). Both labels lapse when new content is pushed, but not when a push only merges in `main`. GitHub records which integration posted each comment and label; the gate requires a review to come through the claimed agent's own integration (Claude Code's is `claude`, Codex's is `chatgpt-codex-connector`), and rejects `espen-approved` when any agent integration added it. Beyond that it is an honest-agent protocol with an audit trail, not security; the setup checklist states the limits and the optional machine account. Agents must never apply `espen-approved` or `espen-override`.

**Keeping PRs current and reviewed.** The gate never merges a PR tested against an older `main`. When `main` moves, the author agent merges `main` into its branch and pushes; approvals carry over if its own changes are unchanged. Authors address every finding in a request for changes and ask that reviewer to look again. The daily digest's "Waiting on agents" list shows each ready PR that waits for a review or an update; The hourly coworker task checks for reviews owed by Codex. Separately, Espen enabled automatic code reviews on pushes; their output and gate compatibility must be verified. See the ongoing-work setup below.

**Reverts.** Merge commits only: no squash, rebase or force-push on `main` or anyone else's branch. To undo a merged PR, open a revert PR (`git revert -m 1 <merge commit>`); it goes through the same gate at the tier of the change it reverts, and reverting Espen-approved work needs Espen. Any agent may open a revert PR for an auto-merged change that broke checks or was misclassified, and should say why in its description.

**Asking Espen.** Put a decision to Espen by labeling the PR or an issue `needs-espen`, stating the question and the options in plain words at the top of its description, and adding it to the queue's "waiting on Espen" list. The daily digest issue (label `agent-digest`) lists what merged, what waits on Espen and which headline numbers moved. Do not ask them to run commands or relay files.

A useful independent review attempts to break the result: a double-counted baseline, missing household group, inadequate reserve, optimistic take-up or behavioral assumption, or an alternative that does the same job for less. It need not repeat every test or ask a different model to endorse the prose. When agents disagree on a project element, compare the evidence and consequences and make a documented decision under the delegation; return genuine goal conflicts to Espen. Do not settle substantive questions by model majority vote.
